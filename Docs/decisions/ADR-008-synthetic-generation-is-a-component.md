# ADR-008 — Synthetic document generation is a component, not tooling

**Status:** accepted · **Decided:** 2026-08-05
**Supersedes:** — · **Related:** [[ADR-002-two-stage-ocr]], [[ADR-006-two-deployment-profiles]], [[EVAL_AND_GOLDEN_SET]]

> **Numbering:** requested as "ADR-007", but that number was taken on 2026-08-05 by
> [[ADR-007-classification-on-the-document-record]]. This is ADR-008. Nothing else about the
> decision changed.

## Context

**There is no public dataset of mixed Urdu/English business documents.** Not a small one, not a
bad one — none. Searching Hugging Face for Urdu OCR datasets returns seven repositories, and
every one of them is prose or verse transcription:

| Dataset | Size | What it is |
|---|---|---|
| `PuristanLabs1/urdu-ocr-1M` | 1.5 M | synthetic Nastaliq lines |
| `deepcopy/MMU-OCR-21-Urdu-TextLines` | 100 K–1 M | text lines |
| `Khurram123/urdu-poetry-nastaleeq-ocr` | 17,610 | poetry couplets |
| `Khurram123/urdu-poetry-ocr-couplets` | 11,700 | poetry couplets |
| `oddadmix/qaari-0.1-ocr-urdu-news-dataset-small` | 35.9 K | news articles — see [[DATASETS]] |
| `tfxhk/urdu_ocr`, `ebadhussain20/urdu_ocr` | small / gated | unlabelled, one is gated |

Zero contain an invoice, a purchase order, or a contract. Zero carry field-level annotation. Zero
mix Urdu and English in one document, which is what a real PTCL commercial document does on every
page. Three independent searches run outside this repository reached the same conclusion; the table
above is this repository's own check, and it agrees.

Absence of a search result is not proof of nonexistence, so state the falsifier plainly: **one
public dataset of annotated bilingual Pakistani business documents would weaken this ADR
substantially.** Nobody has found one.

Meanwhile [[PROJECT_CONTEXT]] §6 INV-6 forbids a real PTCL document from reaching a hosted API,
[[ADR-006-two-deployment-profiles]] establishes that the prototype runs on public and synthetic data
only, and the golden set of 150 real documents does not exist yet and cannot be used on the
prototype when it does. So for the entire prototype phase, **synthetic documents are not a
supplement to the training and eval corpus. They are the corpus.**

## Decision

**Synthetic document generation is a first-class component of this system, not a script in
`tools/`.** It lives under `backend/app/`, it is versioned, its output is stamped, and it is
covered by the same rules as any other component.

Concretely:

1. **It is a pipeline-adjacent component**, not developer tooling. `tools/degrade.py` is tooling —
   it perturbs an image somebody else made. A generator that *invents the documents the model is
   trained and measured on* determines what the model learns and what every accuracy number means.
   That is not a utility.
2. **The generator has a version, and it is stamped on anything derived from it.** A corpus
   generated by generator 0.2 is not comparable with one from 0.1, exactly as
   `pipeline_version.profile` made two extractions incomparable across profiles
   ([[ADR-006-two-deployment-profiles]]). Same failure, same fix.
3. **The field schema comes from FBR SRO 1006(I)/2021**, the Pakistani sales-tax invoice
   requirements. Generating against a published regulatory schema rather than against our own
   `EXTRACTION_SCHEMA.json` is the point: if we invent both the documents and the fields we expect
   to find in them, the eval measures self-consistency and nothing else. SRO 1006(I)/2021 is an
   external constraint we did not choose, which is what makes it useful.
4. **Changing the generator triggers the same obligations as changing a gate**: it updates
   [[EVAL_AND_GOLDEN_SET]], and any accuracy number measured before the change is not comparable
   with one measured after.

### What this does not decide

It does not decide the generator's implementation. Synthdog-RTL was evaluated and **cannot be used
as-is** — it emits page-level plain-text transcription with no field structure and no coordinates,
and it has no bidi support at all. The findings are in [[DATASETS]]. Whether we fork it, build on
`synthtiger` directly, or compose documents from a template engine is an open question in
[[PROJECT_CONTEXT]] §7, not a decision here.

## Reason

The one thing this project cannot buy, download, or borrow is data that looks like a PTCL invoice.
Everything else in the stack is off-the-shelf: PaddleOCR, Qaari, Qwen, FastAPI, Postgres. The
generator is the only piece whose absence stops the project, and the only piece nobody else has
built.

Treating it as tooling has a predictable failure mode, and this repository has already been bitten
by the shape of it three times ([[ADR-003-deterministic-gates]], [[ADR-005-mrc-otc-relationship-unspecified]],
the boolean `gates[].passed`): a thing that is *actually* load-bearing gets classified as
incidental, so nobody versions it, nobody tests it, and its defects become properties of every
number downstream that nobody can see. An unversioned generator means an unversioned eval set, which
means every accuracy figure in this project's history becomes unattributable the first time someone
tweaks a font list.

There is a live example in [[DATASETS]]: the Qaari news corpus is missing the character **آ**
entirely. That defect is invisible in the model card, invisible in the reported 0.048 WER, and would
be invisible in any CER we measured against it. That is what an unexamined corpus does, and we would
be generating ours.

## Consequences

**Accepted:**

- **It has to be built.** No public dataset shortcut exists; this is now on the critical path
  rather than adjacent to it, and the prototype cannot produce a quotable number until it works.
- **`PROJECT_CONTEXT` §3 gains a stack row** and §7 gains the open questions this ADR deliberately
  leaves open.
- **A generated corpus is versioned and stamped**, which means storage and provenance discipline
  for something that used to be regenerable on a whim.
- **Synthetic accuracy still is not real accuracy.** This ADR raises the generator's status; it does
  not raise the status of its output. [[EVAL_AND_GOLDEN_SET]] §2's synthetic-data caveat stands
  unchanged, and the release gates still apply to the real golden set only. Promoting the generator
  to a component makes that caveat *more* important to keep, not less — it is now the thing most
  likely to be quietly forgotten.
- **FBR SRO 1006(I)/2021 has not been read into this repository yet.** The field list it mandates
  is not transcribed anywhere here, and the mapping from those fields onto
  [[EXTRACTION_SCHEMA.json]] is unwritten. Until that exists, item 3 is a decision without an
  implementation.

**Rejected alternatives:**

- *Keep it in `tools/` next to `degrade.py`.* Rejected: see Reason. The two are different kinds of
  thing — one perturbs data, the other creates the ground truth.
- *Use Synthdog-RTL directly and accept line-level labels.* Rejected on evidence, not preference:
  it produces neither field boxes nor structured JSON, and cannot render a mixed-script line
  correctly. [[DATASETS]] §2.
- *Wait for real documents and skip synthesis.* Rejected: real documents are `restricted` under
  INV-6, unusable on the prototype, and do not exist in the repository yet. Waiting means no
  measurement of any kind for the entire prototype phase.
- *Hand-label a few hundred real documents instead.* Not rejected — **deferred and complementary.**
  It is what [[EVAL_AND_GOLDEN_SET]] §2's golden set already requires. Synthesis covers training
  volume and the degraded-input sweep; hand labels cover truth. Neither substitutes for the other,
  and this ADR is not an argument that it does.

## Revisit when

A public bilingual business-document dataset appears, or the golden set of real documents reaches a
size where synthetic training data stops changing the numbers. Also revisit if the generator's
output starts being used to justify an accuracy claim outside `EVAL_AND_GOLDEN_SET` §1's rule —
that would be the signal that promoting it to a component was read as promoting its output to
evidence, which is the opposite of what this says.
